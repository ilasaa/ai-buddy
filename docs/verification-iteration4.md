## Реализованные функции

- Полноценный персональный план: ожидания, даты, цели, критерии, задачи, прогресс и следующие шаги.
- Согласование руководитель → стажёр, комментарии и предложения изменений, номера версий и сохранённые снимки. Изменение согласованного содержания требует новой версии и повторного согласования.
- Редактирование черновика, целей и задач без новых дублирующих моделей задач; проверка сроков и принадлежности цели.
- Самостоятельное подтверждение, проверка результата наставником/руководителем, мини-тесты. Backend запрещает обход проверки прямым статусом `done`.
- История доказательств, повторных отправок, замечаний и решений. Руководитель отдельно подтверждает достижение критериев цели.
- Собственные цели/ожидания/прогресс/OKR из PostgreSQL в чате; безопасные инструменты чтения. Тест отдельно проверяет работу только с `LLM_API_KEY` при пустом `DEEPSEEK_API_KEY`.
- Обращения к назначенному наставнику с сохранением вопросов и ответов; защита от чужой команды/неназначенного наставника.
- Корпоративные заявки предыдущей итерации сохранены, добавлена связь с задачей и форма подготовки из задачи. Создание и согласование не завершают задачу автоматически и не выдаются за фактическое получение доступа.
- Реальные показатели задач, целей, заявок, времени решения и доли ответов ассистента с источниками.
- Три синтетических теста (по 3 вопроса) с сохранённым серверным ключом и порогом 2/3, историей попыток и объяснениями.
- Идемпотентный seed: существующие пользователи сохранены; добавлены новый профиль для полного сценария и отдельный профиль для обзора состояний.
- Dockerfile backend и frontend, Nginx, запуск миграций/seed/CPU-модели/индексации, постоянный кэш модели.

## Архитектура и база данных

План принадлежит стажёру, его ожидания определяет руководитель команды. Цели относятся к плану; существующие `OnboardingTask` связываются с целями. Проверки выполняют только уполномоченные люди либо детерминированный сервис тестов. ИИ получает разрешённый контекст пользователя из БД и ищет инструкции через RAG. Корпоративный инструмент готовит предложение, явная кнопка пользователя вызывает авторизованный backend и демонстрационный адаптер. Все результаты сохраняются транзакционно в PostgreSQL.

## Frontend

Существующая оболочка, маршруты, авторизация, темы и стили сохранены. `/onboarding` теперь показывает персональную адаптацию стажёра либо карточку выбранного доступного стажёра для наставника/руководителя. Стажёр согласует план, отправляет результаты, проходит тесты и видит историю. `/requests` поддерживает подготовку связанной заявки; существующие карточки подтверждения переиспользуются.

## Запуск

При первом развёртывании:

```bash
cp .env.example .env
# Задать собственные POSTGRES_PASSWORD, DEMO_PASSWORD (>=12), JWT_SECRET (>=32), LLM_API_KEY.
sudo docker compose up --build -d
sudo docker compose ps
```

Открыть `http://localhost:8080`. При доступе Docker без sudo — `docker compose up --build -d`. Уже существующий пользовательский `.env` автоматически не заменялся: внесите новые переменные вручную, сохранив текущие пароли и имя базы. Для существующей БД нельзя заменять пароль PostgreSQL без согласованного изменения роли в самой БД. Не удаляйте `postgres_data` и не используйте `down -v`.

Ключ организатора подключается через `.env`, без изменения исходников. Приоритет `LLM_API_KEY` над `DEEPSEEK_API_KEY`, `LLM_MODEL` над `DEEPSEEK_MODEL`; основной провайдер DeepSeek, модель `deepseek-flash`. Секреты не передаются браузеру.

## Демонстрация

Подробный воспроизводимый порядок — [demo-scenario.md](demo-scenario.md): руководитель создаёт план нового стажёра → стажёр согласует → чат читает ожидания → заявка из задачи с явным подтверждением → назначенный ответственный принимает решение → стажёр отправляет практический результат → наставник проверяет → обновляется прогресс → руководитель видит состояние и отдельно подтверждает критерии цели.

Для полного пути: `intern-new@ai-buddy.example`. Для обзора разных состояний: `intern-ready@ai-buddy.example`. Готовый профиль явно маркирован как синтетический seed; его события не выдаются за реально проведённое пользователями согласование.

## Ограничения и непроверенные сценарии

- Docker socket недоступен; `sudo -n` требует пароль. Контейнерная сборка, первый/повторный запуск Compose на PostgreSQL 17 не запускались. Конфигурация проверена статически, миграции/seed/индексация — отдельно на PostgreSQL 18.
- Ручной браузерный E2E, визуальная проверка новых форм на мобильном экране, внешний HTTPS и Cloudflare не выполнены. Frontend проверен компонентными тестами jsdom и сборкой.
- Настоящий запрос к DeepSeek с ключом организатора нужно проверить отдельно только по явной команде. Универсальная совместимость со всеми LLM не гарантируется.
- Реальной выдачи корпоративного доступа нет; согласование не завершает задачу. Jira/Confluence используют наставника как явно назначенного демонстрационного ответственного, GitLab — руководителя вместо владельца проекта.
- Нет отдельных официальных чек-листов других специализаций, графа зависимостей задач, фонового планировщика, внешних уведомлений, MCP-сервера, feature flags и запросов отсутствия. P2 не реализовывался.
- Мини-тесты подготовлены авторами прототипа; редактор вопросов и утверждение вопросов LLM не реализованы. Обращение наставнику отправляется явной формой, автоматической отправки из чата нет.
- У одного стажёра один текущий план; предыдущие согласованные версии доступны снимками. `completed`/`archived` зарезервированы, автоматического перехода плана к ним нет.
- Эффект на сроки адаптации и нагрузку наставника не измерен. Методика гипотез приведена в [metrics.md](metrics.md); A/B-тест не заявляется.
