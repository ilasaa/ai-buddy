# Корпоративные действия: исполняемая спецификация

## Цель и границы

Стажёр команды `Backend · Demo` оформляет доступ к Jira, Confluence или GitLab,
проект `BACKEND`, права `read`/`write`. Это синтетическая политика демо, не политика Авито.
Заявка сохраняется в PostgreSQL. Одобрение не выдаёт доступ в реальный сервис.

## Выбор инструментов

Используется существующий OpenAI-совместимый Chat Completions клиент: `tools` с функциями
и JSON Schema, `tool_choice=auto`. Для DeepSeek thinking отключён. Контракт сверялся
11.11.2026 с https://api-docs.deepseek.com/guides/tool_calls/ (пример deepseek-flash).
Beta strict не требуется: Pydantic с `extra=forbid` проверяет аргументы на сервере.
Провайдер, отвергающий tools, получает безопасную ошибку 503 без резервного исполнения текста.
Автотесты подменяют LLM; реальная совместимость конкретного стороннего провайдера требует smoke-проверки.

Маршрутизация учитывает текущую тему и короткие ответы с параметрами. Новая явная тема
(например, Code Review) завершает оформление доступа в контексте маршрутизатора.
Подготовка заявки и чтение статуса не вызывают RAG: найденный конфликт не блокирует действие.
Вопрос «Как получить доступ?» сохраняет RAG, но посторонние документы и конфликты отбрасываются.
Исторические ответы о конфликте Code Review исключаются из контекста оформления доступа.
Вопрос о своих задачах также получает инструменты. Обычные внутренние вопросы используют RAG;
общие вопросы — LLM. При отсутствии инструкций по доступу инструменты остаются доступны:
права задаёт серверная политика, а не найденный документ. При отсутствии других корпоративных
источников backend сообщает о недостатке информации. Известный конфликт обрабатывается до LLM.

| Инструмент | Аргументы | Эффект |
| --- | --- | --- |
| create_access_request | resource: jira/confluence/gitlab; project_key: BACKEND; permission: read/write; justification: 5–1000 символов | Только черновик |
| get_access_request_status | request_id: положительное целое | Проверка видимости и текущая запись БД |
| list_my_access_requests | пустой объект | Только собственные заявки |
| get_my_onboarding_tasks | пустой объект | Существующий onboarding.overview |

Модель уточняет сервис, проект и права; backend не угадывает их. Инструмент принимает
неполные аргументы и возвращает конкретный вопрос только о недостающих полях. Перед
сохранением черновика применяется полная схема AccessArguments. Причина необязательна
в инструменте: по умолчанию «Работа над задачами стажировки», видимая в карточке.
Уточняющий текст модели сохраняется, а не заменяется технической ошибкой. В аргументах нет user_id,
team_id, approver_id или роли. Неизвестные инструменты, SQL и произвольные HTTP запрещены.
Один платный проход выбора инструментов, максимум четыре вызова и один черновик на сообщение;
повторных циклов или платной переформулировки результатов нет. Результаты форматирует backend.
Если при явной просьбе оформить/проверить заявку модель не вызвала инструмент, backend
сообщает, что операция не выполнена. Обычный текст модели никогда не меняет состояние.

## Подтверждение

Черновик `ActionProposal` хранит UUID, владельца, команду, неизменяемые параметры,
диалог, состояние и expires_at (10 минут). Клиент передаёт только UUID.
Prepare может вызываться отдельным API, но заявки не создаёт.
Confirm повторно проверяет текущего пользователя, роль, активность, команду и политику.
Параметры JSON в confirm не используются: редактирование возможно только новым черновиком.
Подтверждённый UUID возвращает ту же заявку; отменённый/истёкший — 409.
Cancel повторяем, но подтверждённый черновик отменить нельзя.

Подготовка и подтверждение сериализуются `pg_advisory_xact_lock(18429,user_id)`;
черновик дополнительно блокируется `FOR UPDATE`. Уникальный proposal_id в заявке защищает
повторное исполнение. Одинаковые активные черновики переиспользуются; отдельный черновик
не создаст дубль существующей pending/approved заявки с тем же сервисом, проектом и правами.
После rejected разрешено подать новую заявку. Заявка, состояние черновика и событие создаются
одной транзакцией. При потере ответа повторяют confirm того же UUID, без генерации новых параметров.
Внешних побочных эффектов у demo-адаптера нет. Реальная интеграция потребует отдельного
контракта идемпотентности и восстановления после сетевых ошибок внешнего сервиса.

## Ошибки и безопасность

401 — нет сессии; 403 — политика/роль/CSRF; 404 — чужой объект скрыт;
409 — срок/состояние/дубликат; 422 — схема HTTP; 503 — БД/неподдерживаемый API/провайдер;
429 — лимит; 504 — тайм-аут LLM. Секреты и ошибки провайдера не возвращаются клиенту.
Инструменты получают только текущего пользователя из HttpOnly JWT cookie.
Изменения требуют разрешённый Origin и `X-Requested-With: AI-buddy`.
RAG и история — недоверенные данные. Даже prompt injection может максимум подготовить
видимый черновик: confirm недоступен модели. Ручной вызов confirm авторизованным владельцем
с тем же Origin — эквивалент явного подтверждения; API без серверного черновика заявки не создаёт.

Проверки: `backend/tests/test_access.py`, `frontend/src/Access.test.tsx`.
Ограничение: эвристическая маршрутизация инструментов; выбор инструмента моделью не гарантирован.
